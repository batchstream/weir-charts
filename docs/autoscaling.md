# Autoscaling

How to scale a Store group with KEDA and Prometheus.

## Example overlay

Overlay [examples/prometheus-autoscaling.yaml](../examples/prometheus-autoscaling.yaml) on the `mongo` release in namespace `application`. Adjust the namespace, release identity, Prometheus endpoint and scraper labels for your deployment. Its query sums this exact group's Weir process CPU; `AverageValue` lets HPA divide that total across replicas, and the threshold of 1.4 cores is 70% of the default per-replica limit, so change it with `resources`. Scale on Weir's own CPU, not on queued operations or active executions: those rise whenever the backend slows down, and replicas added then bring no capacity, so a queue trigger holds the group at its maximum. Each replica runs fewer record batches at once while executions queue in its backend, so the group's combined requests follow what the backend can take rather than the replica count; a new replica starts at two batches per operation for a little over one probe interval after its first execution, so replicas added in front of a queueing backend do not flood it; the dashboard shows that limit and the latency ratio behind it. Set `maxReplicaCount` from the backend's connection budget: each replica runs up to 16 record batches and 64 Natives per Store at once.

## Query guard and coverage

The example guards its aggregate with `and on() (min(up{namespace="application",weir_group="application/mongo"}) == 1)`. A failed discovered scrape target or no discovered targets produces an empty result; `ignoreNullValues: "false"` then leaves KEDA in error instead of treating an incomplete lower workload as a valid scale-down signal. The HTTP timeout is 10 seconds, and no `or vector(0)` supplies a false zero. This guard covers the targets Prometheus has discovered; it cannot prove that scraper configuration includes every group Pod. EndpointSlice discovery keeps a terminating Pod as a target until it is deleted, so its last scrape after exit fails and briefly turns the query into an error; drop endpoints whose `terminating` condition is true, as the default Endpoints discovery already does. Before enabling autoscaling, compare the per-Pod targets with all running/Ready group replicas and verify the labels, `process_cpu_seconds_total` and `up` are present; repeat that coverage check after scale and rollout changes. Configure an existing `TriggerAuthentication`/`ClusterTriggerAuthentication` through `authenticationRef` if needed. No controller credentials are rendered or read by this Chart. KEDA's operator, metrics server and relevant network rules must already allow its Prometheus query. See [the Prometheus scaler contract](https://keda.sh/docs/2.20/scalers/prometheus/) and [ScaledObject specification](https://keda.sh/docs/2.20/reference/scaledobject-spec/).

## KEDA settings and turning autoscaling on

`autoscaling.triggers` accepts native KEDA triggers, including Prometheus and other supported scalers. Prometheus triggers require metrics to be enabled; CRDs/controllers are external prerequisites. `pollingInterval`, `cooldownPeriod` and `scaleDown` configure polling and HPA scale-down behavior. The cooldown setting concerns KEDA activation/scale-to-zero; ordinary reduction between running replica counts is controlled by HPA behavior. Minimum replicas must stay at least one: SDK connections cannot wake a group with zero replicas. A PDB requires at least two minimum replicas. Every upgrade or rollback that turns autoscaling on removes the Chart's replica count, so Kubernetes resets the Deployment to one replica until KEDA's HPA scales it to `minReplicaCount`: from three replicas with a minimum of two, two Pods were terminating within 20 seconds and the second Ready replica returned after about a minute. Turn autoscaling on when one replica can carry the load, with `minReplicaCount` at least the running count. `kubectl apply` and GitOps tools reset the count the same way when they turn autoscaling on. Upgrades that keep autoscaling on leave the count to KEDA. Verify the ScaledObject becomes Ready and HPA reaches its minimum before admitting production traffic; Helm readiness alone does not establish controller readiness. Disabling KEDA resumes the configured `replicaCount`.
